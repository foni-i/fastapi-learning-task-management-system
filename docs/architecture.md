# Architecture

## System context

The service is a modular monolith: one FastAPI application and one PostgreSQL
database. Docker Compose supplies repeatable local infrastructure. GitHub Actions
will run the same quality commands used locally.

```text
HTTP client
    -> FastAPI middleware (request ID, logging, error translation)
    -> /api/v1 Router and dependencies
    -> Pydantic request schema
    -> Service/use case (rules, authorization, transaction)
    -> Repository (owned/scoped query)
    -> SQLAlchemy synchronous Session
    -> PostgreSQL
    -> response schema -> HTTP response
```

The future Agent path reuses the same domain boundary rather than creating a
second persistence stack:

```text
Authenticated request or controlled CLI
    -> Agent run boundary (trusted user identity)
    -> LangGraph node
    -> strict Agent tool schema
    -> Domain service (authorization and transaction)
    -> Repository
    -> SQLAlchemy synchronous Session
    -> PostgreSQL
```

Nodes and tools never query the database directly. This keeps HTTP and Agent
entry points consistent and makes business rules independently testable.

authorization to create empty directories early.

## Layer responsibilities

| Layer | Owns | Must not own |
| --- | --- | --- |
| Router | HTTP input, dependency injection, response model, status code | SQL queries or substantial business rules |
| Schema | External/internal data shape and validation | Persistence or transaction behavior |
| Service | Use-case rules, authorization orchestration, state transitions, transaction boundary | FastAPI response details |
| Repository | SQLAlchemy queries and persistence operations | HTTP errors, independent commits, policy decisions |
| Model | Table mapping, relationships, indexes, database constraints | API serialization contracts |
| Core | Configuration, security primitives, logging, common exceptions | Feature-specific business workflows |

Use functions where sufficient. A layer boundary does not require a class for
every operation.

## Dependency direction and request lifecycle

Routers depend on services and schemas. Services depend on repositories and
domain/model types. Repositories depend on SQLAlchemy models and the supplied
session. Models and core utilities do not depend on routers.

A database dependency creates one synchronous Session per request and closes it
after the response path. Each write use case owns one explicit transaction.
Repositories call `flush` when generated values are needed but do not call
`commit`; exceptions leave the use case responsible for rollback. Read use cases
do not commit.

Agent tools call the same service functions as routers. A trusted request/run
context supplies the authenticated user ID outside model-controlled arguments.
Synchronous database calls remain behind service boundaries; LangGraph alone is
not a reason to migrate the application to AsyncSession.

Authorization is defense in depth:

1. The authentication dependency validates the access token and resolves the
   current user.
2. The service passes that user's ID to every user-owned repository operation.
3. Repository predicates include both resource ID and owner ID.
4. Missing and foreign-owned resources share the documented 404 behavior.
5. Database foreign keys and service checks keep task and project ownership
   consistent.

## Data design

The MVP tables are `users`, `refresh_tokens`, `projects`, and `tasks`. All use
PostgreSQL UUID primary keys generated by a database default. Foreign keys and
frequently filtered columns receive indexes based on actual query patterns.

Important invariants are protected twice when practical: friendly validation or
business errors in schemas/services, plus database constraints for integrity
under concurrent or non-HTTP writes. Examples include unique normalized email,
project date order, positive estimates, and task/project relationships.

All persisted timestamps are timezone-aware UTC. `created_at` and `updated_at`
are assigned consistently by the persistence layer. Public schemas emit ISO 8601
values with an offset. Calendar dates remain SQL `date` values.

Refresh tokens are independent database records containing only a keyed or
cryptographic hash, expiration, revocation state, rotation lineage as required,
and non-sensitive metadata. Raw tokens exist only at issuance/verification
boundaries.

Agent persistence has three separate concerns:

1. Domain data remains in `users`, `projects`, and `tasks` and is changed only
   through domain services.
2. Agent business records contain thread/run identifiers, approval decisions,
   executed-tool summaries, outcomes, errors, and metrics needed for audit and
   product behavior.
3. LangGraph checkpoints use the official persistence schema and lifecycle for
   graph recovery. Checkpoint rows are not a substitute for business audit data.

Graph state stores serializable identifiers and validated values, never Sessions,
connections, ORM objects, provider clients, API keys, or hidden model reasoning.

## API and error design

Product endpoints live under `/api/v1`; health endpoints remain unversioned.
Request, update, internal, and response schemas are separate where their allowed
fields differ. Response schemas whitelist fields rather than serializing ORM
objects indiscriminately.

Domain exceptions carry a stable code, safe message, optional details, and HTTP
status mapping. Global handlers add the current request ID and translate both
domain and Pydantic validation errors into the common envelope. Unexpected errors
are logged with context while returning a generic response.

## Configuration, observability, and security

Settings come from environment variables through pydantic-settings. A committed
`.env.example` documents names but contains no real secrets. Production startup
fails early when required secrets are missing or unsafe.

Middleware creates or validates a request ID, records structured request
metadata, and measures duration. It never logs authorization headers, cookies,
complete tokens, passwords, secret settings, or request bodies containing
credentials. CORS uses an explicit origin list.

Password and JWT behavior use maintained libraries. No custom cryptography is
implemented. Access JWT validation checks signature, expiration, token type, and
configured issuer/audience. Refresh-token rotation is transactional so a token
cannot be successfully reused after rotation.

Model provider keys are secret settings and never enter state, logs, traces, or
test fixtures. Tool names and arguments are allowlisted and validated before
execution. High-impact writes pause for explicit approval and carry idempotency
keys so retry or resume cannot duplicate work. Retrieved documents are untrusted
context and cannot override authorization, approval, or tool policies.

Tracing records prompt version, node/tool names, safe input summaries, outcomes,
latency, token usage, and errors. It does not record complete credentials,
Authorization headers, sensitive model payloads, or chain-of-thought.

## Testing strategy

- Unit tests exercise pure validation, security helpers, and service rules with
  controlled dependencies.
- API integration tests exercise routing, dependencies, transactions, real
  PostgreSQL constraints, and cross-user isolation.
- Integration tests use a dedicated PostgreSQL test database, never the
  development database. Tests clean state transactionally or through explicit
  fixtures.
- Migration checks start from an empty database, upgrade to head, downgrade as
  required by the stage, and upgrade again.
- Quality gates are pytest, Ruff lint, Ruff format check, and mypy.
- Provider adapters are replaceable with deterministic fakes. Ordinary tests
  never require network model calls; external-provider tests use a separate
  marker and explicit credentials.
- Nodes and tools are tested independently. Prompt changes run versioned offline
  regression evaluations before acceptance.

SQLite is not treated as equivalent to PostgreSQL. Small pure unit tests may not
need a database, but database integration behavior is proven against PostgreSQL.

## Deliberate tradeoffs

- Synchronous SQLAlchemy is easier to teach and debug for this workload; async
  can be reconsidered only with measured need.
- UUIDs make public identifiers opaque and portable, at the cost of larger
  indexes than integer keys.
- A modular monolith keeps deployment and transactions simple while retaining
  clear feature boundaries.
- Explicit services and repositories clarify policy and persistence boundaries;
  trivial behavior should not be inflated with empty abstractions.
